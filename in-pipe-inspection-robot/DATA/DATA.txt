# IN PIPE INSPECTION ROBOT — COMPLETE PROJECT SPECIFICATION AND TECHNICAL CONTEXT

## 1. Project Identity and Overview

The project is named **IN Pipe Inspection Robot**. It is an ESP32-based robotic system designed to travel inside or along a pipe or cylindrical inspection environment and allow an operator to control its movement wirelessly while observing the inspection area through a camera. The system combines embedded electronics, wireless communication, motor control, an onboard camera, proximity sensing, distance measurement, LED illumination, battery-powered operation, and a smartphone application created using MIT App Inventor. The primary objective is to provide a remotely operated inspection platform capable of moving forward and backward, displaying live camera footage, measuring the distance to nearby objects, detecting obstacles using an infrared sensor, and controlling an inspection light. The system is intended to be compact enough for a pipe-inspection application and should ultimately operate without requiring a laptop to remain connected. The operator uses a smartphone as the control interface, while the robot's electronics execute the commands and provide feedback. The project is intended to be documented as an engineering project, so explanations, diagrams, code, and report content must distinguish between the intended design, the connections previously configured, the features reported as working, and the features that still require testing or confirmation.

## 2. Mechanical Design and Chassis

The robot uses a compact chassis intended to fit within or travel along the inside of a pipe. The mechanical concept uses a PVC pipe or cylindrical central body, with an approximate body diameter of 2.5 inches and an intended body length of around 30 cm. These dimensions are design estimates rather than verified final manufacturing dimensions. The mechanical concept includes six wheels or wheel-like supports arranged approximately 120 degrees apart around the body, with three supports on each side. Four yellow TT-type DC geared motors drive the four powered wheels, while the remaining two wheels or supports are passive. The four powered motors must operate together to move the robot in a straight line. The required movement modes are forward, backward, and stop. The design does not require independent left/right movement, sideways movement, or differential steering. The chassis should support the motor assembly, electronics, battery, camera, inspection light, and sensors while protecting the wiring from contact with the pipe walls. Foam-sheet pieces were considered for the supporting legs or wheel structures. Final wheel geometry, mounting brackets, actual chassis dimensions, camera orientation, and the physical arrangement of the electronics must be confirmed against the completed prototype.

## 3. Main Controller: ESP32 Development Board

The principal controller used in the design is an ESP32 development board, commonly selected in the Arduino IDE as “ESP32 Dev Module.” The ESP32 provides GPIO pins for motor-driver control, sensor input, LED switching, and wireless communication. The original combined firmware was written in C++ using the Arduino framework and included the WiFi.h and WebServer.h libraries. The controller connects to a Wi-Fi network, starts an HTTP server on port 80, receives movement requests from the smartphone application, operates the motor driver, and provides sensor readings through an HTTP endpoint. The ESP32's IP address is obtained from the network and can be printed in the Arduino IDE Serial Monitor. The phone and robot controller must be connected to the same reachable network for the local HTTP commands to work.

The principal GPIO assignments in the previously configured motor and sensor firmware are GPIO25 for L298N ENA, GPIO26 for IN1, GPIO27 for IN2, GPIO14 for ENB, GPIO32 for IN3, and GPIO33 for IN4. GPIO18 is assigned to the HC-SR04 TRIG signal, GPIO19 to the HC-SR04 ECHO signal through suitable voltage protection, GPIO23 to the IR obstacle sensor output, and GPIO13 is the planned output for the LED MOSFET gate-control circuit. These assignments must be preserved when updating compatible firmware unless there is a documented reason to change them. A revised program must not accidentally assign the same GPIO to two incompatible functions. GPIO availability, boot-strapping restrictions, and the specific development-board layout should be checked before adding further hardware.

## 4. L298N Motor Driver and Four DC Gear Motors

The robot uses one L298N dual H-bridge motor-driver module to control four yellow TT-type DC geared motors. Since the L298N provides two motor channels, the intended arrangement is to connect two motors in parallel to one channel and the other two motors in parallel to the second channel. This allows all four motors to receive the same directional commands using the two channels. The driver must be suitable for the combined current drawn by the motors, including starting and stall current; the fact that four motors can be connected electrically does not guarantee that one L298N can safely supply them. Motor current, driver temperature, voltage drop, and cooling must be checked before prolonged operation.

The motor-control pin mapping is as follows:

- L298N ENA → ESP32 GPIO25.
- L298N IN1 → ESP32 GPIO26.
- L298N IN2 → ESP32 GPIO27.
- L298N ENB → ESP32 GPIO14.
- L298N IN3 → ESP32 GPIO32.
- L298N IN4 → ESP32 GPIO33.

The two enable pins, ENA and ENB, are used for motor enable and speed control. When pulse-width modulation (PWM) is used, the enable jumpers on the L298N module must be configured according to the module design; the relevant jumper must be removed when external PWM control is required. The direction input pins select the polarity applied to each motor channel. For forward motion, both motor groups receive the appropriate forward logic state; for backward motion, the direction states are reversed; for stop, the firmware must disable the motors or command a safe stopping state. The actual forward and backward logic states should be established by testing the motor orientation because motors mounted on opposite sides may need their leads reversed to ensure that the robot physically travels in the same direction.

The four motors are arranged as follows: Motor 1 is the left-front motor, Motor 2 is the left-rear motor, Motor 3 is the right-front motor, and Motor 4 is the right-rear motor. The intended electrical arrangement connects Motor 1 and Motor 2 in parallel to one L298N channel, and Motor 3 and Motor 4 in parallel to the other channel. The exact physical assignment of OUT1, OUT2, OUT3, and OUT4 must be confirmed from the actual driver module and wiring. In the earlier connection plan, OUT1/OUT2 were used for one motor group and OUT3/OUT4 for the other. Both groups must be coordinated by the ESP32 so the robot moves forward or backward without attempting to steer.

The previous firmware used a PWM frequency of 1000 Hz, an 8-bit PWM resolution, and a motor-speed value of 128. An 8-bit duty value of 128 corresponds to approximately 50.2% PWM duty cycle because the nominal range is 0–255. This does not mean that the physical motors rotate at exactly 50% of their maximum speed; actual speed depends on the motor, battery voltage, mechanical load, and the voltage drop across the L298N. A later revision of the software should preserve these settings if compatible with the selected Arduino-ESP32 core, or document any required changes to the PWM API.

The motor power supply must be connected to the L298N motor-power input at a voltage appropriate for the motors and driver. The logic ground, ESP32 ground, motor-driver ground, and supply ground must be common where required by the circuit. The ESP32 GPIO pins must never be used to supply motor current directly. The L298N handles the motor current, while the ESP32 provides only low-current logic signals.

## 5. ESP32-CAM Camera Subsystem

The robot includes a separate ESP32-CAM board for visual inspection. The camera subsystem captures the view inside the pipe and makes it available to the smartphone over Wi-Fi. The ESP32-CAM is a separate board from the main motor-control ESP32, and it must have its own suitable power supply. The intended operating arrangement places the camera board and motor-control board on the same phone hotspot or compatible Wi-Fi network so the smartphone can communicate with both. The camera does not need a direct serial connection to the motor-control ESP32 during ordinary Wi-Fi video streaming unless a separate serial-control feature is deliberately implemented.

The camera firmware uses the ESP32 camera framework, including esp_camera.h, WiFi.h, a board configuration header such as board_config.h, and functions such as startCameraServer() and setupLedFlash(), depending on the installed camera example and board configuration. The camera's actual GPIO configuration must match the specific ESP32-CAM hardware. Camera pin assignments must not be copied from an unrelated ESP32 development board because the ESP32-CAM has dedicated camera signals and different pin constraints.

When the ESP32-CAM joins the network successfully, its local IP address is displayed in the Serial Monitor or otherwise obtained from the network. The operator can open the camera webpage through the IP address. Depending on the camera firmware, the root address may display a camera-control webpage, while a separate stream endpoint may provide the video alone. In a common CameraWebServer arrangement, the stream endpoint is often available on port 81 at /stream, but the exact endpoint must be checked against the firmware that is actually installed. The application should use the real URL provided by the running camera server rather than assume every ESP32-CAM sketch uses the same address.

The MIT App Inventor app uses a WebViewer component to display the camera webpage or stream. The design has considered two approaches: automatically opening a configured camera address, or allowing a camera URL to be entered or pasted when needed. A fixed address is convenient but can stop working if the hotspot assigns the camera a different IP address. If the camera's address changes, the app's configured URL must be updated unless address reservation or another reliable discovery method is implemented. The camera board must receive stable regulated power capable of handling its Wi-Fi and camera current peaks. If a USB programming adapter is used for uploading, the ESP32-CAM can normally operate without that adapter after programming, provided a suitable independent supply is connected to the correct power pins.

The camera's Wi-Fi and streaming firmware must remain separate from the motor-control firmware unless the project architecture is intentionally redesigned. The camera provides video; the main ESP32 handles the motor and sensor endpoints. The two systems share the Wi-Fi network, not necessarily their program memory, GPIO pins, or internal processing resources.

## 6. HC-SR04 Ultrasonic Distance Sensor

The robot uses an HC-SR04 ultrasonic sensor to measure the distance to the nearest object in front of the sensor. The sensor has four connections: VCC, TRIG, ECHO, and GND. The configured GPIO assignments are TRIG → ESP32 GPIO18 and ECHO → ESP32 GPIO19. The VCC connection should use a supply appropriate for the actual sensor module, commonly 5 V for a standard HC-SR04. The sensor ground must connect to the common circuit ground.

A standard HC-SR04 can produce an ECHO signal close to 5 V. Because ESP32 GPIO inputs are not 5 V tolerant, the ECHO signal must be reduced to a safe logic voltage using a suitable voltage divider or level-shifting circuit. A representative divider uses a 1 kΩ series resistor between ECHO and the GPIO node and a 2 kΩ resistor from the GPIO node to ground; the resulting voltage is approximately two-thirds of the input voltage, so a 5 V ECHO signal becomes approximately 3.3 V. The actual resistor values and wiring must be checked before powering the sensor. Supplying a standard HC-SR04 from 3.3 V does not automatically guarantee that the ECHO output is safe, nor does it guarantee reliable sensor operation.

The firmware generates a trigger pulse on GPIO18 and measures the duration of the returned ECHO pulse on GPIO19. It converts that duration into a distance in centimetres. The earlier code used a pulseIn timeout of approximately 30,000 microseconds and returned -1 if no echo was detected. The distance endpoint, such as /distance, can return the numerical distance as text or a status such as NO ECHO when a valid measurement is unavailable. The app should display the returned value appropriately. If the response is NO ECHO, the interface should not append “cm” to that text as though it were a valid distance.

The ultrasonic sensor is intended to provide a numerical distance measurement. It is not necessarily responsible for assigning near, medium, or far categories. The IR sensor is the separate device intended for basic proximity detection. These functions should remain distinct in the software and report.

## 7. IR Obstacle/Proximity Sensor

The project includes an IR obstacle-detection module. The signal output pin is connected to ESP32 GPIO23 in the previously configured design. The module's VCC and GND must be connected according to its rated supply voltage and the specific board's documentation, and its output logic level must be safe for the ESP32. Some IR modules produce a LOW signal when an object is detected, while others may have different logic behaviour depending on the module and its adjustment. The earlier firmware used the setting IR_DETECTED_LEVEL LOW, meaning LOW was treated as obstacle detected. This assumption must be verified against the actual sensor module before finalising the program.

The IR sensor is used to detect the presence of a nearby obstacle or surface within the sensor's effective range. It does not provide a reliable numerical distance measurement in centimetres in the same way as an ultrasonic sensor. Its detection range can depend on surface colour, reflectivity, ambient lighting, sensor adjustment, and physical alignment. The app may display an IR state such as “Obstacle Detected” or “Clear,” provided the software implements and returns those states. If the current code only reads the sensor internally and does not expose the result through an HTTP endpoint, the app cannot display that state until an endpoint and the corresponding app logic are implemented.

## 8. LED Inspection Light and MOSFET Driver

The inspection lighting subsystem uses a 12 V DC LED strip or bar, described as approximately 1.5 W with three LEDs in the original hardware description. Its estimated current at 12 V is 1.5 W / 12 V = 0.125 A, or approximately 125 mA, assuming the stated power rating applies to the whole strip. The LED strip must not be connected directly to an ESP32 GPIO because the GPIO cannot safely supply its operating current or voltage.

The intended switching component is an IRLZ44N logic-level N-channel MOSFET, with a 220 Ω gate resistor and a 10 kΩ gate-to-ground pull-down resistor. The proposed control GPIO is GPIO13. The low-side switching arrangement is as follows: connect the positive terminal of the 12 V supply to the LED strip's positive input; connect the LED strip's negative output to the MOSFET drain; connect the MOSFET source to the common ground; connect ESP32 GPIO13 to the MOSFET gate through the 220 Ω resistor; and connect the 10 kΩ pull-down resistor between the gate and ground. The power supply ground and ESP32 ground must be common for the control signal to work correctly. The precise IRLZ44N pin order must be checked from a reliable datasheet for the exact component and package before wiring it; the physical pin order must not be guessed from the appearance of the component.

The MOSFET must be suitable for operation with a 3.3 V gate-control signal. Although the IRLZ44N is commonly used as a logic-level MOSFET, its suitability for the actual load and operating conditions should be checked from its datasheet. The LED strip receives power from its appropriate supply, not from GPIO13. The MOSFET acts as an electronic switch controlled by the ESP32.

The intended software behaviour is to provide LED On and LED Off commands from the smartphone application. If the main ESP32 web server implements endpoints such as /led/on and /led/off, those requests can switch the output state and return a response. These endpoint names represent the proposed or previously discussed interface and must be checked against the current source code before being documented as implemented. The firmware should set GPIO13 to a known safe state during initialisation so the LED does not unintentionally turn on during boot.

## 9. Battery, BMS, and Voltage Regulation

The planned power system uses a three-cell lithium-ion battery pack with three 18650 cells connected in series. The cells were described as 3.7 V nominal cells, with an earlier stated capacity of approximately 4300 mAh per cell. A three-cell series pack has a nominal voltage of approximately 11.1 V and a fully charged voltage of approximately 12.6 V. The pack is intended to provide power to the motor driver and, through suitable regulation, the lower-voltage electronics.

The battery system includes a 3S battery management system (BMS) intended to provide battery protection and cell balancing if the selected board supports that function. The BMS must be suitable for the battery chemistry, cell configuration, maximum charge/discharge current, and the motor load. A BMS does not repair damaged cells, make mismatched cells safe, or replace a compatible charger. The pack should be charged only using an appropriate charger for a 3S lithium-ion pack. Any cell suspected of damage, abnormal heating, or significant voltage imbalance must be inspected by a qualified person and must not be forced to charge or bypassed.

A buck converter is planned to reduce the battery voltage to a regulated 5 V supply for compatible electronics. The output voltage must be adjusted and verified with a multimeter before connecting the ESP32 or ESP32-CAM. The regulated output must remain within the input requirements of the connected boards under realistic load conditions. A 5 V rail must not be connected to an ESP32 3V3 pin, and 12 V must never be connected directly to an ESP32 GPIO or 3V3 pin. The ESP32-CAM generally requires a stable 5 V input at its designated 5 V pin when powered through that input, whereas the exact power arrangement for the main ESP32 board depends on the board's VIN/5V circuitry. The correct pin must be verified from the actual board markings and schematic.

The L298N motor supply and the regulated electronics supply have different purposes. The motor supply connects to the L298N's motor-voltage input at the voltage permitted by the motors and driver. The regulated 5 V output powers only those devices that are designed to accept 5 V. The LED strip uses its appropriate 12 V supply, with the MOSFET controlling its return path. All subsystems that exchange electrical signals must share a common reference ground where required. Power rails must not be joined indiscriminately: the battery, regulator, motor driver, and electronics must be connected according to their actual input requirements and the final power-distribution schematic.

A possible capacitor arrangement across the regulated supply and ground can help reduce brief voltage dips or electrical noise if correctly selected and installed. However, capacitors cannot repair a damaged regulator, a shorted board, an incorrect power connection, or an overloaded supply. A board that heats rapidly must not be repeatedly powered for experimentation. Any abnormal heating of the ESP32 module, voltage regulator, buck converter, battery, or wiring requires the power source to be disconnected and the circuit to be checked safely before further testing.

## 10. Wi-Fi Communication Architecture

The system uses Wi-Fi as the wireless communication method. The original network configuration used a phone hotspot, and the design later used the network name PIPEROBOT in the main controller code; an earlier configuration used a different hotspot name. The final network name and credentials should be read from the latest source files rather than assumed from an old code version. The credentials must not be published in a public project report.

The intended network arrangement connects the smartphone, the motor-control ESP32, and the ESP32-CAM to the same Wi-Fi network, usually a smartphone hotspot. The phone sends HTTP requests to the motor-control ESP32's IP address, while the camera stream is opened through the ESP32-CAM's IP address. Each ESP32 has its own network address and its own firmware. The camera and motor-control boards do not automatically share the same IP address merely because they use the same network. The two devices should be identified separately in the app and the report.

The main ESP32 code uses WiFi.h and WebServer.h and starts an HTTP server on port 80. The previous application design used movement endpoints such as /forward, /backward, and /stop, with /distance used for the ultrasonic measurement. LED endpoints such as /led/on and /led/off were discussed as the interface for lighting. The exact endpoint names and response format must match the firmware currently uploaded. An HTTP endpoint must be implemented in the code before the application can use it successfully.

The robot is intended to be controlled without continuous USB connection to a computer. Once the firmware is uploaded, the ESP32 boards should operate from suitable independent power sources. The laptop is used for programming, serial monitoring, and troubleshooting rather than as a permanent operating component. A local Wi-Fi network may stop working if the hotspot is disabled, its IP addresses change, or the phone and devices cannot communicate with one another. The application should show clear connection status and provide a safe way to stop the motors if communication is lost.

## 11. Smartphone Application Using MIT App Inventor

The smartphone application is developed using MIT App Inventor and is named “Pipe Inspection Robot” in the earlier app design. It is intended to provide a single user interface for operating and observing the robot. The app includes movement controls, a camera-viewing area, distance display, connection status, vehicle state, and LED control. The app communicates with the main ESP32 using HTTP requests and displays the camera webpage or stream through a WebViewer component.

The movement interface has Forward, Backward, and Stop buttons. When the user presses Forward, the app sends an HTTP request to the main ESP32's forward endpoint. The ESP32 interprets the request and sets the motor-driver outputs to the forward state. Backward sends the corresponding backward command, while Stop sends the stop command. The app should not assume that a request succeeded simply because the button was pressed; a returned response or subsequent status check is needed to confirm the result. The user previously reported that the motor controls were working in the app, but the latest firmware and hardware must be tested again before the complete system can be described as fully operational.

The application also includes or is intended to include a vehicle-state label displaying states such as “Stopped” and “Moving,” plus an ESP32 connection-status label displaying “Connected” or “Disconnected.” The design goal is to avoid repeated disruptive error pop-ups and instead display connection problems in a label or other non-intrusive status indicator. If a Web component fails to contact the ESP32, the app should handle the error gracefully and not continuously trigger blocking alerts. The app may use a Clock component to periodically request sensor data, but the polling interval should be chosen to avoid excessive requests or repeated errors. A 500 ms interval was discussed for distance updates.

For distance display, the app can use a Web component such as WebDistance with its URL set to the main ESP32's /distance endpoint. The ClockDistance timer calls WebDistance.Get periodically. The WebDistance.GotText event then updates a label such as LabelDistance.Text with the response. A display string could be “Distance: 9 cm” when the response is a valid numeric value. If the server returns NO ECHO or another error message, the app should display the status without incorrectly adding the cm unit. The app's distance display must use the response actually returned by the endpoint rather than a hard-coded value.

The camera section uses the MIT App Inventor WebViewer component. Its HomeUrl or current URL should be set to the camera webpage or correct stream endpoint. A refresh or Connect Camera button may instruct the WebViewer to reload the configured camera address. Earlier development considered automatically setting a fixed camera IP address and later considered restoring a link-pasting option. The final implementation should follow the latest working app design. If a fixed IP is used, the app needs to be updated when the camera's address changes unless a stable address is configured. If a pasted URL is used, the user should be able to enter or paste the correct address and load it safely. The WebViewer should be large enough to show the stream or camera webpage without hiding the motor controls, and its layout should support scrolling if the full camera control page is larger than the screen.

The LED interface has LED On and LED Off controls. The On button should send the corresponding HTTP request to the ESP32 and cause GPIO13 to drive the MOSFET gate-control circuit. The Off button should turn that GPIO off. The app should update the lighting status only when its logic indicates that the command was successfully processed. The LED strip's current is supplied through the external power circuit, not through the smartphone app or the GPIO itself.

MIT App Inventor components likely relevant to this design include Buttons for Forward, Backward, Stop, LED On, LED Off, and camera refresh; Labels for distance, connection status, and vehicle state; a Web component for HTTP requests; a WebViewer for camera video; a Clock component for periodic sensor requests; and possibly a Notifier for non-blocking or occasional user feedback. If the camera URL is stored for later use, TinyDB may be used to remember the address. These are the intended component roles; the actual Designer screen and Blocks must be inspected to confirm which components are present in the current project.

## 12. Main ESP32 Firmware Structure

The previously configured main controller firmware uses C++ in the Arduino environment. It includes WiFi.h and WebServer.h, declares the network credentials, defines the L298N pins, configures the sensor pins, sets the motor PWM parameters, creates a WebServer on port 80, and defines handlers for incoming HTTP requests. The firmware should initialise the motor control pins to a safe state, configure the sensor pins, establish Wi-Fi connectivity, print the assigned IP address to the Serial Monitor, register the HTTP routes, and start the web server.

The motor-control handler for the forward command sets the direction inputs and enables the motor channels. The backward handler reverses the required direction states. The stop handler disables the motor channels or sets the safe stop condition. The loop function services incoming web requests and can periodically read sensors if that is how the final firmware is structured. The earlier code printed the ultrasonic distance approximately every 500 ms. The implementation must avoid long blocking operations that prevent the HTTP server from servicing a Stop command quickly.

The ultrasonic distance function triggers the HC-SR04 and measures the ECHO pulse using a timeout. If no pulse is returned, the function should report an invalid measurement instead of producing a misleading numerical distance. The IR sensor input can be read as a digital HIGH or LOW according to the actual module's logic. The LED-control function sets GPIO13 to the appropriate output state when an HTTP command is received. The final source code must consistently use the same pin assignments and route names throughout the program.

The ESP32-CAM firmware is a separate program. It configures the camera pins for the actual camera board, connects to the Wi-Fi network, starts the camera server, and reports its network address. Its configuration should be based on the correct camera board model and the matching camera example. The main ESP32 and ESP32-CAM should not run duplicate or conflicting motor-control logic unless the architecture explicitly calls for it.

## 13. Original and Revised Controller Architecture

The original design placed motor control, sensor readings, Wi-Fi communication, and LED control on a single ESP32 development board, while the camera ran on a separate ESP32-CAM. During later development, heating and controller reliability became a concern, and a plan was discussed to divide the robot's functions across two ordinary ESP32 boards plus the separate ESP32-CAM. Under that proposed split, one ESP32 would be dedicated to motor-driver control, while the second ESP32 would handle other functions such as sensors, LED control, and related communication. The ESP32-CAM would remain responsible for video streaming.

This division is a proposed architecture and should not be represented as a confirmed, functioning three-board implementation unless the relevant firmware and wiring have been completed and tested. If two normal ESP32 boards are used, the report must identify which board owns each GPIO, which board hosts the HTTP endpoints, how commands and sensor readings are exchanged, and whether both boards connect independently to the same Wi-Fi network or communicate over another interface. Each GPIO belongs to its own physical board; GPIO13 on one ESP32 is not the same electrical pin as GPIO13 on another ESP32. The final design should keep the motor stop behaviour reliable even if the other controller or camera is unavailable.

## 14. Electrical Grounding and Signal Protection

The ESP32, L298N logic interface, sensor outputs, MOSFET control circuit, and regulated power supply require correct ground referencing. All grounds that exchange signals must be connected according to the final power schematic. The motor-current return path should be arranged carefully so that motor noise and current surges do not destabilise the logic supply. A common ground does not mean that every positive supply voltage should be connected together. The 12 V motor supply, regulated 5 V rail, and 3.3 V logic rail have different functions and must be connected only through appropriate supply inputs and regulators.

The ESP32 GPIOs are designed for 3.3 V logic and must not receive 5 V signals directly. The HC-SR04 ECHO output needs level protection when it can reach 5 V. The IR module output must be checked for compatible logic voltage. The ESP32-CAM must receive power through the appropriate input pin, and the LED strip must use the external power circuit and MOSFET. The L298N motor driver must be operated within its current and thermal limits. Wiring should be checked against the actual component pin labels, module schematics, and datasheets before power is applied.

## 15. Development Tools and Testing Environment

The firmware is developed using the Arduino IDE, with the ESP32 board package installed. A board such as ESP32 Dev Module is selected for the main ESP32 where appropriate. The ESP32-CAM may require a separate board selection and camera configuration. The USB-to-serial interface is used to upload firmware and inspect serial output. The Wi-Fi address can be obtained from the Serial Monitor. MIT App Inventor is used to build the Android application and arrange the interface and event blocks. Wokwi and Cirkit Designer were previously considered for simulation or circuit design, but any simulation should be clearly identified as a simulation rather than proof that the physical robot works.

Testing should be performed in stages. First, verify the regulated power supplies and grounds with the boards disconnected. Next, test the controller by itself, then verify the motor driver and one motor channel with an appropriate current-limited or otherwise protected test arrangement. Confirm that the forward, backward, and stop commands behave correctly before connecting all four motors. Test the ultrasonic sensor and IR sensor separately, verify the sensor voltage levels, and then integrate them into the main firmware. Test the MOSFET and LED circuit separately using the correct power supply and wiring. Test the ESP32-CAM and camera stream independently. Finally, connect the smartphone app to the main ESP32 and camera, confirm that the correct IP addresses and endpoints are used, and test the complete system.

The robot should be tested with the wheels safely clear of obstructions before movement tests. Motor startup current, L298N temperature, supply stability, Wi-Fi latency, camera streaming, and sensor readings should be observed during integration. If an ESP32 board or power component heats rapidly, disconnect power and do not continue repeated power tests. A rapid-heating board may have a damaged regulator, an internal short, a wiring fault, or another electrical problem. A multimeter resistance or continuity reading alone is not sufficient to identify the exact failure. A damaged board or lithium-ion battery pack should be assessed safely before being used again.

The IN Pipe Inspection Robot is a Wi-Fi-controlled robotic inspection platform combining a motorised chassis, four DC geared motors, an L298N dual H-bridge driver, an ESP32 control board, a separate ESP32-CAM video subsystem, an HC-SR04 ultrasonic distance sensor, an IR proximity sensor, a MOSFET-switched 12 V LED inspection light, a lithium-ion battery pack with BMS, and a regulated power supply. The main firmware uses Arduino C++, Wi-Fi communication, and an HTTP server to accept commands and return sensor readings.
